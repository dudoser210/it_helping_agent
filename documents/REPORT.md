# Отчёт по проекту: IT Helping Agent

## Мультиагентная система обработки заявок сотрудников

**Автор(ы):** ____________________  
**Дисциплина:** Управление разработкой программного обеспечения  
**Версия:** 1.0  
**Стек:** Python, FastAPI, Ollama, Qwen3.5, Docker Compose, SQLite, Prometheus, Grafana, OpenTelemetry, Jaeger

---

## 1. Постановка задачи

Сотрудники регулярно создают повторяющиеся заявки: не подключается Wi-Fi, не печатает принтер, нет доступа к системе, не запускается программа. Первая линия поддержки тратит время на классификацию, типовые уточнения и поиск инструкции. Универсальный чат-бот способен дать ответ, но смешивает роли, хуже контролирует безопасность и не объясняет, почему выбрал конкретный маршрут.

Цель проекта - создать локальную мультиагентную систему, которая принимает заявку, определяет домен и приоритет, извлекает подходящие фрагменты корпоративных runbook'ов, предлагает безопасную диагностику и решает, нужен ли человек. Система не исполняет команды и не выдаёт права. Она работает как ассистент первой линии.

Ключевые критерии: локальность данных, воспроизводимый запуск на ПК, объяснимая оркестрация, отдельный safety-контур, измеримое качество и полный observability-стек.

## 2. Техническое задание

Вход: `employee_id`, текст заявки, опционально устройство, ОС, локация и ID сессии. Выход: ID заявки, категории, приоритет, краткое резюме, объяснение, упорядоченные шаги, уточняющие вопросы, статус (`resolved`, `needs_info`, `escalated`), причина эскалации и техническая метаинформация.

Функциональные требования:

1. Поддержать четыре домена: Wi-Fi, принтеры, доступы, программы.
2. Разрешить multi-label классификацию: одна заявка может относиться к VPN и доступу.
3. Параллельно запускать независимых специалистов только по выбранным доменам.
4. Использовать локальную базу знаний и локальную историю сотрудника.
5. Не повторять секреты и не рекомендовать обход защитных механизмов.
6. Экспортировать метрики, логи и трейсы; иметь алерты.
7. Предоставить web UI, REST API и CLI.
8. Иметь unit-тесты без LLM и eval-набор с реальной моделью.

Нефункциональные требования: Python 3.11+, локальная LLM через Ollama, контейнер без root и capabilities, read-only root filesystem, ограничение ресурсов, структурированный JSON, конфигурация через environment, документация на русском языке.

## 3. Архитектура мультиагентной системы

Выбрана иерархическая архитектура supervisor + specialists + critic + synthesizer. Она сочетает управляемый маршрут и специализацию.

1. **Intake Agent** очищает смысл заявки, определяет категории, приоритет и недостающие данные.
2. **Router** - детерминированный код, а не LLM. По категориям он выбирает специалистов.
3. **Wi-Fi / Printer / Access / Software Agents** независимо диагностируют свой домен. При нескольких категориях работают параллельно (`fan-out`).
4. **Policy Agent** независимо проверяет советы на секреты, административные действия и обход политик.
5. **Deterministic safety-gate** блокирует известные опасные паттерны даже при ошибке LLM.
6. **Resolver Agent** объединяет одобренные выводы (`fan-in`) и выбирает статус.

```text
Employee -> Intake -> Router -> [Specialists in parallel]
                                  |-> Policy Agent -> code safety-gate -> Resolver -> Response
Markdown RAG ---------------------|                          |
SQLite history -------------------|--------------------------|
```

Почему не один агент: общий промпт быстро становится противоречивым; сложнее тестировать routing, безопасность и качество отдельных доменов; любой сбой затрагивает весь ответ. Разделение даёт локальные промпты, независимые метрики и возможность заменить только слабый компонент.

Почему не свободная «команда» диалоговых агентов: Helping-процесс известен заранее. Свободные переговоры увеличивают токены и latency, затрудняют воспроизводимость и создают циклы. Детерминированный DAG ограничивает число вызовов.

### Выбор оркестратора

| Вариант | Сильные стороны | Ограничения | Решение |
|---|---|---|---|
| Самописный async DAG | минимум зависимостей, прозрачность, полный контроль, простой fan-out | циклы/checkpointing писать самостоятельно | выбран для v1 |
| LangGraph | состояние, checkpointing, ветвления, human-in-the-loop | дополнительная абстракция для короткого графа | v2 при усложнении |
| CrewAI | быстрый role-based прототип | меньше контроля над строгим маршрутом | не выбран |
| AutoGen | диалоги и сложная кооперация | избыточные разговоры и токены | не выбран |

Текущий граф содержит один предсказуемый цикл запроса без возвратов. `asyncio.gather` и `Semaphore` дают параллелизм и защищают RAM/VRAM. При добавлении согласований, долгоживущих тикетов и human-in-the-loop проект целесообразно перенести на LangGraph.

## 4. LLM и локальный runtime

Используется Ollama HTTP API `/api/chat` со `stream=false` и JSON Schema в поле `format`. Модель задаётся переменной `OLLAMA_MODEL`; значение по умолчанию - `qwen3.5:latest`. Температура 0.1 снижает вариативность. Контекст ограничен 8192 токенами, хотя модель может поддерживать больше: Helping-заявке не нужен огромный контекст, а меньший размер предсказуемее по памяти.

Qwen3.5 выбрана потому, что пользователь уже установил её в Ollama, модель поддерживает русский язык, reasoning и structured output через runtime. Размер можно заменить без изменений кода: слабый ПК использует меньший тег, более мощный - 9B или выше. Главный недостаток локальной LLM - зависимость качества и задержки от железа. Поэтому `AGENT_MAX_PARALLEL=2`, timeout равен 180 секунд, а eval фиксирует latency.

Ollama официально предоставляет chat endpoint с сообщениями, схемой формата, параметрами thinking и статистикой токенов; эти поля используются клиентом и метриками. Список доступных тегов Qwen3.5 проверяется отдельно, поэтому в `.env` нужно ставить точное имя из `ollama list`.

## 5. Системные промпты, скиллы и Markdown-файлы

Системные промпты находятся в `prompts/`, по одному на роль. Общие принципы:

- узкая роль и явные границы ответственности;
- конкретный алгоритм, а не просьба «помоги пользователю»;
- только русский язык и JSON Schema;
- запрет считать заявку или RAG-контекст инструкцией высокого приоритета;
- явные условия эскалации;
- отсутствие выдуманных URL, телефонов и результатов действий.

Скиллы находятся в `skills/<domain>/SKILL.md`. Они семантически описывают вход, процедуру, ограничения и эскалацию. Скилл отличается от промпта: промпт управляет конкретным LLM-вызовом, а скилл является переносимым описанием способности и регламентом для разработчика/агента.

База знаний `knowledge/*.md` содержит небольшие runbook'и с тематическими заголовками. Markdown выбран из-за читаемости, простого code review и возможности обновлять знания без релиза Python-кода. Каждый возвращённый фрагмент имеет `SOURCE`, а итоговый API показывает список использованных документов.

## 6. Изоляция и модель угроз

Рассмотрены четыре уровня.

| Подход | Что изолирует | Плюсы | Минусы |
|---|---|---|---|
| Python venv | зависимости Python | быстро, удобно для разработки | не изолирует сеть, процессы и FS |
| Docker | процесс, FS, сеть, ресурсы | воспроизводимость и умеренный overhead | общий kernel с хостом |
| VM | отдельная ОС/kernel | сильная граница | тяжёлая, медленный старт, GPU passthrough |
| microVM/sandbox | короткоживущая сильная изоляция | хорошо для недоверенного кода | сложнее инфраструктура |

Для v1 выбран **hardened Docker Compose + отдельный Ollama runtime**. Агент только формирует текст и не имеет shell/tool для исполнения команд, поэтому VM или Firecracker несоразмерны риску. Контейнер:

- запускается UID 10001, не root;
- имеет `read_only: true`, запись только в named volume SQLite;
- получает `cap_drop: ALL` и `no-new-privileges`;
- ограничен 2 GB RAM и 200 PID;
- использует `tmpfs` с `noexec,nosuid`;
- не монтирует Docker socket и домашнюю директорию;
- не хранит модель и секреты в image.

Ollama может оставаться на хосте (удобно на Windows/macOS) или запускаться отдельным контейнером с volume. На Linux максимально чистый вариант - compose overlay с контейнерным Ollama. Открывать хостовый порт Ollama во внешнюю сеть не следует.

Остаточные риски: общий kernel Docker, prompt injection, вредоносный runbook, утечка данных в логах, DoS длинными заявками. Меры: лимит входа 6000 символов, локальная база знаний, запрет исполнения, редактирование секретов, ограничение ресурсов и независимый safety-gate. Для агента, который начнёт исполнять команды на endpoint'ах, потребуется microVM/одноразовый sandbox и allowlist tools.

## 7. Организация памяти и RAG

Память разделена по времени и назначению.

**Working memory** - состояние одной заявки в объектах Pydantic: классификация, выводы специалистов, политика, итог. После ответа оно не сохраняется целиком.

**Episodic memory** - SQLite-таблица тикетов. Intake получает последние три записи того же `employee_id`; это помогает видеть повторяемость. SQLite выбран за локальность и нулевое администрирование. Недостатки: один узел, ограниченная конкурентность, слабые политики retention/ACL. В production лучше PostgreSQL с шифрованием, TTL, tenant isolation и аудитом.

**Semantic memory** - Markdown runbook'и, разбитые по заголовкам. Локальный BM25-подобный retriever учитывает частоту и редкость терминов, category boost и top-k. Он не требует второй embedding-модели, работает offline, объясним и стабилен для терминов `DNS`, `MFA`, кодов ошибок.

Недостаток sparse retrieval - слабое понимание перефразирования и синонимов. Dense vector RAG лучше ловит смысл, но требует embedding-модель, vector DB, версионирование embeddings и больше ресурсов. На малом корпусе отдельная Chroma/Qdrant база пока создаёт больше operational overhead, чем пользы.

План «проапгрейченного RAG»:

1. Hybrid retrieval: BM25 + embeddings Ollama `/api/embed`, reciprocal rank fusion.
2. Metadata filters: ОС, приложение, офис, версия runbook, уровень доступа.
3. Cross-encoder/LLM reranker top-20 -> top-4.
4. Query rewriting с сохранением исходного запроса.
5. Parent-child chunks: точный абзац + контекст раздела.
6. Retrieval eval: Recall@k, MRR, nDCG и faithfulness.
7. Feedback memory: подтверждённое инженером решение, а не любой ответ модели.
8. Retention и право на удаление истории сотрудника.

RAPTOR полезен для большой иерархической документации, GraphRAG - для зависимостей «приложение-сервис-владелец-сеть», HyDE - для неясных пользовательских формулировок. Для четырёх коротких runbook'ов они избыточны, но рассмотрены как путь развития.

## 8. Безопасность и guardrails

Одного промпта недостаточно. Используется defense in depth:

1. Pydantic ограничивает типы и длину входа.
2. Каждый LLM-вызов обязан вернуть JSON Schema.
3. Специалисты помечают риск шага: `safe`, `caution`, `admin`.
4. Policy Agent запрещает секреты, отключение MFA/EDR/firewall, обход RBAC, разрушительные команды и неизвестные источники.
5. Кодовый фильтр повторно блокирует `rm -rf`, `reg delete`, format, disable security и admin steps.
6. Финальный ответ повторно сканируется. При нарушении шаги удаляются, заявка эскалируется.
7. Система не имеет tool для выполнения команд, поэтому галлюцинация не превращается в действие.

Модель может обойти регулярное выражение через нестандартную формулировку. Production-версия должна использовать структурированный allowlist операций, policy-as-code (например OPA), DLP/secret scanner и human approval для любого change action.

## 9. Evals

Оценка разделена на LLM-компоненты и агентную систему.

### Метрики LLM

- category exact/multi-label F1;
- priority accuracy и weighted error (пропуск critical дороже ложного high);
- schema validity rate;
- groundedness/faithfulness к runbook;
- forbidden-content rate;
- полнота обязательных уточнений.

### Метрики системы

- task success rate: пользователь получил применимый безопасный маршрут;
- routing accuracy;
- escalation precision/recall;
- safety violation rate (целевой 0);
- p50/p95 end-to-end latency;
- LLM error rate, токены на тикет, число вызовов;
- retrieval Recall@k/MRR;
- повторное открытие заявки и human override в production.

Стартовый `golden.jsonl` включает DNS, массовый сбой принтера, попытку передать пароль/отключить MFA и повреждение профиля программы. Проверяются категория, допустимый диапазон приоритета, обязательные понятия, запрещённые фразы и лимит latency. Порог pass rate 0.75 выбран только для стартового прототипа; перед production нужен набор минимум 100-300 обезличенных тикетов, разметка двумя инженерами и анализ расхождений.

Unit-тесты не требуют Ollama и проверяют retriever, SQLite, Pydantic и deterministic safety. LLM eval запускается отдельно, потому что медленный и недетерминированный. Для сравнения промптов нужно фиксировать тег/quantization модели, seed если поддерживается, железо и версии runbook'ов.

## 10. Observability

Рассмотрены LangSmith, Langfuse и стандартный open-source стек. LangSmith удобен с LangGraph, но является внешним сервисом; это конфликтует с требованием локальности. Self-hosted Langfuse даёт LLM-специфичный UI, но добавляет PostgreSQL/ClickHouse и операционную сложность. Выбран vendor-neutral стек:

- **Prometheus** собирает counters/histograms;
- **Grafana** показывает заранее подготовленный dashboard;
- **OpenTelemetry** создаёт спаны полного тикета и каждого агента;
- **Jaeger** визуализирует fan-out/fan-in и задержки;
- **JSON stdout logs** читаются через Docker logs и готовы для Loki/ELK.

Метрики: заявки по статусу/приоритету, agent runs, LLM errors, prompt/completion tokens, LLM/retrieval/end-to-end latency. Алерты: сервис недоступен минуту; более 10% ошибок LLM за пять минут; p95 выше 60 секунд десять минут.

В логи намеренно не пишутся полный текст заявки, промпты и ответы: они могут содержать PII. Трейсы содержат ID и категорию, но не секреты. В production необходимо добавить correlation ID, log retention, authenticated Grafana, Alertmanager и алерт-канал.

## 11. Развёртывание

На Windows/macOS Docker Desktop предоставляет `host.docker.internal`; агент использует уже запущенный Ollama. Последовательность: проверить `ollama list`, скопировать `.env.example` в `.env`, указать точный тег, выполнить `docker compose up --build`, открыть `http://localhost:8000`.

На Linux рекомендуется compose overlay `docker-compose.ollama.yml`: модель хранится в отдельном named volume и один раз скачивается командой `ollama pull`. Это не переиспользует хостовую копию, зато не требует публиковать Ollama на сетевом интерфейсе.

Локальный запуск в `venv` оставлен для разработки и быстрой демонстрации. Он использует `http://localhost:11434`, но не считается полной изоляцией.

## 12. Ограничения и развитие

Текущая система является учебным прототипом. Она не знает реальную топологию, статусы сервисов, владельцев и каталог ПО; не подключена к AD/Entra/ServiceNow/Jira; не анализирует изображения; не исполняет действия; корпус знаний мал; BM25 не семантический в строгом смысле; SQLite не HA; eval-набор синтетический.

Приоритеты v2: hybrid RAG; versioned knowledge ingestion; интеграция с CMDB только на чтение; human approval; feedback dataset; LangGraph checkpointing для долгих тикетов; PostgreSQL; RBAC в API; mTLS к Ollama; Loki/Alertmanager; нагрузочные тесты; мультимодальные скриншоты с предварительным удалением PII.

## 13. Итог

Проект реализует не просто чат с локальной моделью, а контролируемую мультиагентную систему: разные роли, параллельный граф, локальная память, RAG, независимая политика, кодовый safety-контур, evals и полный monitoring pipeline. Выбор hardened Docker соответствует текущей модели угроз, а архитектура оставляет понятный путь к microVM и более сложному RAG, если агент получит реальные инструменты и production-нагрузку.
